# ontology-boundaries.md

## Purpose

This document defines the ontology philosophy and conceptual boundaries of the LLM wiki knowledge system.

The purpose of ontology boundaries is to prevent:

* ontology explosion
* semantic fragmentation
* overlapping page structures
* taxonomy drift
* uncontrolled concept proliferation
* reviewer fatigue
* long-term maintainability collapse

The ontology should remain:

* understandable
* durable
* operationally useful
* cognitively sustainable
* maintainable by a single human operator

over many years.

---

# Core Principle

The ontology should optimize for:

> durable operational understanding

NOT:

> maximal semantic decomposition

The system should strongly prefer:

* fewer stronger concepts
* broad reusable abstractions
* stable conceptual structures
* operationally meaningful boundaries

over:

* highly granular decomposition
* exhaustive semantic separation
* aggressive concept splitting
* rapidly expanding taxonomies

---

# The Primary Failure Mode

The biggest long-term risk is:

> ontology growth exceeding review and maintenance capacity

Symptoms include:

* too many glossary terms
* too many overlapping topics
* tiny how-to pages
* weakly differentiated trends
* excessive tagging
* concept duplication
* routing ambiguity
* reviewer hesitation
* constant taxonomy redesign

The ontology must actively resist this tendency.

---

# Conceptual Compression Over Decomposition

The system should generally prefer semantic compression.

Example:

Prefer:

* trustworthy AI grounding architectures

over separately maintaining:

* provenance
* auditability
* traceability
* explainability
* grounding metadata

unless the distinctions become operationally meaningful.

The ontology should expand only when conceptual distinctions become genuinely useful.

---

# Stable Concepts Over Exhaustive Coverage

The ontology is not intended to model every possible concept.

It is intended to model:

* recurring operational structures
* durable conceptual primitives
* reusable workflow abstractions
* important strategic distinctions

A smaller stable ontology is preferable to a large noisy ontology.

---

# The Purpose Of Each Knowledge Layer

Each layer exists for a different type of understanding.

Maintaining clear boundaries between layers is critical.

---

# Sources

Purpose:

* preserve provenance
* preserve article context
* preserve historical extraction artifacts

Sources are archives.

They are not the primary durable knowledge layer.

Sources should not absorb operational synthesis responsibilities.

---

# Glossary

Purpose:

* durable conceptual reference
* recurring industry terminology
* reusable conceptual primitives

Glossary entries should be:

* reusable
* durable
* operationally meaningful
* semantically distinct

The glossary is NOT:

* a keyword index
* a terminology dump
* an article summary layer

Glossary growth should remain slow and conservative.

---

# Topics

Purpose:

* operational synthesis
* durable architectural understanding
* recurring workflow patterns
* reusable strategic understanding

Topics should represent:

* broader operational themes
* reusable conceptual clusters
* accumulated understanding across sources

Topics are intentionally broader than glossary entries.

---

# How-Tos

Purpose:

* reusable implementation knowledge
* operational workflows
* execution patterns
* practical engineering procedures

How-tos should focus on:

* reusable procedures
* generalized operational patterns

How-tos should avoid becoming:

* tiny setup notes
* fragmented procedural trivia
* micro-pages

---

# Trends

Purpose:

* durable directional industry shifts
* recurring ecosystem movement
* strategic operational changes

Trends should represent:

* persistent movement
* repeated evidence
* strategic significance

Trends are NOT:

* daily news
* temporary hype
* isolated speculation

Trend extraction should remain highly conservative.

---

# Tools

Purpose:

* operational tooling understanding
* workflow positioning
* ecosystem role understanding
* practical applicability

Tool pages should focus on:

* workflow implications
* orchestration implications
* operational strengths/limitations

Tool pages should avoid becoming:

* feature catalogs
* release-note trackers
* exhaustive product documentation

---

# Models

Purpose:

* foundation-model operational understanding
* orchestration implications
* workflow suitability
* capability positioning

Model pages should focus on:

* operational tradeoffs
* ecosystem role
* practical implications

NOT:
benchmark obsession or minor release differences.

---

# Tags

Purpose:

* lightweight metadata
* broad categorization
* retrieval assistance

Tags are NOT primary ontology structures.

Tags should remain:

* shallow
* constrained
* low-maintenance

Tags should not become:

* secondary ontologies
* deep taxonomies
* graph-management systems

---

# Related Terms

Related terms are graph enrichment structures.

They are not primary ontology units.

Related-term generation should generally occur:

* automatically
* lightly
* later in the pipeline

The system should avoid requiring heavy manual curation of semantic graphs.

---

# Ontology Expansion Rules

The ontology should expand slowly.

A new concept/page/category should generally require:

* repeated evidence across sources
* operational usefulness
* conceptual distinctiveness
* long-term durability
* reviewer confidence
* strategic relevance

The ontology should resist:

* one-off concepts
* article-specific framing
* weakly differentiated abstractions
* hype terminology

---

# Semantic Distinctiveness

A new ontology object should only exist if it represents a genuinely distinct operational concept.

The system should ask:

> Does this distinction meaningfully improve understanding or workflow organization?

If not, the concept likely belongs inside an existing structure.

---

# Avoiding Fragmentation

Fragmentation occurs when:

* concepts become too narrow
* pages become too small
* distinctions become too fine-grained
* semantic overlap increases

Fragmentation increases:

* routing difficulty
* reviewer hesitation
* maintenance burden
* retrieval ambiguity
* conceptual instability

The ontology should aggressively resist fragmentation.

---

# Broad Concepts Are Often Better

Broad durable concepts are often preferable to narrow precise ones.

Example:

Prefer:

* context engineering

over many tiny fragmented pages such as:

* prompt compression
* retrieval ranking
* context pruning
* token budgeting
* context stitching

unless these become independently important over time.

---

# Concept Lifecycle Philosophy

Concepts should emerge gradually.

The ontology should support:

* uncertainty
* deferred decisions
* gradual stabilization
* incremental refinement

Not every extracted proposal should immediately become a permanent ontology object.

---

# Deferred Ontology Decisions

Deferral is healthy.

The system should support:

* uncertain concepts
* emerging patterns
* tentative trends
* provisional routing

The ontology should stabilize slowly through repeated evidence.

---

# Source-Type Awareness

Different source types naturally generate different ontology pressures.

---

## Roundups

Roundups generate many weak signals.

The ontology should strongly resist creating new objects from isolated roundup observations.

---

## Interviews

Interviews often contain speculative abstractions.

The ontology should prefer durable operational synthesis over personality-driven framing.

---

## Medium Articles

Medium articles often encourage over-extraction because they:

* repeat concepts heavily
* over-frame central ideas
* introduce weak abstractions
* generate semantic redundancy

The ontology should remain conservative.

---

# Ontology Stability Over Speed

Rapid ontology growth is dangerous.

Stable long-term structures are more valuable than fast conceptual expansion.

The system should prefer:

* slower growth
* fewer concepts
* repeated reinforcement
* stronger synthesis

over aggressive ingestion-driven expansion.

---

# Human Attention Economics

Ontology maintenance consumes long-term human attention.

Every new:

* glossary entry
* topic
* trend
* tag
* category

creates permanent maintenance cost.

Ontology expansion should therefore be treated as an expensive operation.

---

# Anti-Goals

The ontology should avoid becoming:

* a semantic graph of everything
* a maximalist knowledge graph
* a taxonomy obsession system
* a benchmark archive
* a keyword universe
* a concept explosion machine
* an automatically expanding wiki

The goal is operational intelligence accumulation.

Not semantic completeness.

---

# Long-Term Philosophy

The ontology should evolve conservatively and intentionally.

A smaller number of durable, operationally meaningful knowledge structures is more valuable than a rapidly expanding conceptual universe.

The highest-quality knowledge systems are not the most exhaustive.

They are the most stable, understandable, and reusable over long periods of time.
