# Technical Specification: Data Ownership, Retention, and Cleanup

Last updated: 2026-07-11

This specification defines which data in `llm-wiki-karpathy` is canonical,
which data is generated, which data is temporary, and which data should be
versioned, backed up, or deleted.

It is intended for an implementation agent that has no prior chat context.

## Purpose

The current repository contains code, raw sources, review artifacts, synthesis
cache entries, generated wiki pages, previews, run reports, and backups.

That was useful during development, but it creates too many overlapping
structures. The user wants a maintainable product, not a pile of intermediate
folders.

The system must preserve enough data to:

- read original sources from Obsidian and by agents
- regenerate the generated wiki
- understand where a synthesis came from
- roll back consistently
- audit important automated runs

At the same time, it should not permanently keep every debug artifact, preview,
backup, or duplicate rendered view.

## Core Rule

Use this rule throughout the implementation:

> Data that is canonical or needed for regeneration must be preserved. Data
> that can be regenerated from canonical data should be treated as generated or
> temporary. Temporary data should have a cleanup policy.

## Data Classes

### Canonical Data

Canonical data is the durable truth of the knowledge system.

If canonical data is lost, the system cannot fully reconstruct the same
knowledge state.

Canonical data includes:

- original raw source exports
- human-reviewed extraction artifacts
- final Stage 2 synthesis cache entries
- release manifests that bind a coherent state together
- configuration used for extraction, rendering, and synthesis

### Generated Data

Generated data is useful and may be versioned, but it can be recreated from
canonical data plus code.

Generated data includes:

- rendered Obsidian wiki pages
- rendered source pages for Obsidian
- rendered indexes
- `state/wiki_render_graph.json`
- `state/wiki_render_manifest.json`

The render graph and render manifest are generated, but important enough to
store with releases because they make rollback and agent access easier.

### Temporary Data

Temporary data is for review, debugging, and operational observation.

Temporary data includes:

- synthesis previews
- synthesis run reports
- synthesis backups
- prompt previews
- ingest batch logs
- transient local caches

Temporary data should not become a permanent second knowledge layer.

## Recommended Retention Policy

### Preserve Permanently

Preserve:

- `raw/readwise/`
- `state/reviews/`
- `state/synthesis/`
- release manifests
- private notes and meeting notes

These are either original evidence or canonical human/model-reviewed knowledge.

### Preserve Per Release

Preserve with each release:

- graph hash
- manifest hash
- rendered wiki hash
- source page hash
- reviews hash
- synthesis hash
- raw snapshot id
- code commit
- relevant config hashes

Do not preserve every temporary file forever. Preserve the release summary.

### Clean Automatically After Successful Release

After a successful release, the system may clean:

- `state/synthesis_previews/`
- old `state/synthesis_backups/`
- old prompt previews

Previews are redundant once:

1. the synthesis cache entry exists under `state/synthesis/`
2. `wiki-render` has rendered the page
3. the release manifest records the rendered output

### Retain Temporarily

Retain run logs for a bounded period:

- default: latest 30 days or latest 100 run reports
- keep failed run reports longer than successful run reports
- summarize important run facts into release manifests

The exact cleanup command can be implemented later. This specification only
defines the policy.

## Git Policy

Git should not be used as an unlimited archive for all raw and temporary data.

Recommended:

- Code repo uses Git normally.
- Vault repo uses Git for generated wiki pages, indexes, and possibly source
  Markdown pages.
- Canonical knowledge state can be Git-versioned if size remains manageable, or
  captured by release snapshots if it becomes large.
- Raw HTML should not be Git-versioned by default.
- Temporary folders should not be Git-versioned by default.

Important:

Rollback must not rely on only rolling back `wiki/`. A consistent rollback must
restore a full knowledge release.

## Backup Policy

Raw data and canonical knowledge state need real backups.

Suggested backup technologies:

- `restic`
- `rsync` to a server
- Hetzner Storage Box
- S3-compatible object storage
- filesystem snapshots

The first implementation should not choose a backup provider automatically. It
should only make paths and release manifests ready for reliable backup.

## Release Manifest

Introduce a release manifest concept before destructive cleanup.

Suggested path:

```text
state/releases/<release_id>.json
```

Suggested release id:

```text
20260711T230000Z
```

Suggested fields:

```json
{
  "release_id": "20260711T230000Z",
  "created_at": "2026-07-11T23:00:00Z",
  "code_commit": "abc123",
  "config_hashes": {
    "review_tags_topics": "...",
    "review_tags_trends": "..."
  },
  "raw_snapshot": {
    "strategy": "external-backup",
    "snapshot_id": "restic:...",
    "raw_dir": "/srv/llm-wiki/data/raw/readwise"
  },
  "reviews_hash": "...",
  "synthesis_hash": "...",
  "graph_hash": "...",
  "manifest_hash": "...",
  "wiki_hash": "...",
  "sources_hash": "...",
  "indexes_hash": "...",
  "counts": {
    "raw_sources": 362,
    "reviews": 360,
    "synthesis_entries": 120,
    "wiki_pages": 614
  },
  "temporary_artifacts": {
    "synthesis_previews_cleaned": true,
    "synthesis_runs_summarized": true,
    "synthesis_backups_cleaned": true
  }
}
```

The first implementation may create a simpler release manifest. It must be
extensible.

## Rollback Model

A rollback should target a release, not an individual folder.

Rollback target:

```text
release_id = 20260711T230000Z
```

A consistent rollback must restore or verify:

- code commit
- raw snapshot availability
- review artifacts
- synthesis cache entries
- render graph
- render manifest
- generated wiki
- generated source pages
- indexes

If only the rendered wiki is rolled back, the system is inconsistent. Avoid
that.

## Source Text Access Policy

The private Obsidian vault must expose full source text in a directly clickable
way.

Requirement:

- generated wiki pages link to full source pages
- full source pages are readable Markdown
- agents can open the same source pages from local paths
- users do not need to copy external URLs or manually search another folder

The full source page may be generated from raw Markdown/HTML. The original raw
export remains preserved separately.

## Team/Public Policy

The private vault may include full source text.

A future team/public view must be treated separately.

Default:

- private vault: full sources allowed
- team vault/site: generated wiki pages allowed
- team vault/site full source exposure: explicit later decision
- personal notes and meeting notes: never included in team/public export by
  default

This avoids blocking the user's primary use case while keeping future sharing
safe.

## Cleanup Safety Rules

No cleanup command should delete canonical data.

Cleanup commands must:

- default to dry-run
- show what would be deleted
- only delete temporary paths
- refuse to run if no successful release manifest exists
- never delete `raw/`, `state/reviews/`, or `state/synthesis/`
- have tests for path safety

Suggested future command:

```bash
hatch run wiki-cleanup --dry-run
hatch run wiki-cleanup --after-release 20260711T230000Z --yes
```

This command is not part of the first implementation unless explicitly scoped.

## Implementation Phases

### Phase 1: Document and Enforce Classification

- Add this policy to docs.
- Add `.gitignore` rules for temporary folders if missing.
- Add a lint/status check that reports temporary artifacts separately from
  durable artifacts.

### Phase 2: Release Manifest Prototype

- Add a read-only or dry-run release manifest generator.
- It should hash key folders and report counts.
- It should not clean anything yet.

### Phase 3: Source Page Generation

- Generate full readable source pages from raw exports.
- Link wiki pages to source pages.
- Keep original raw files as backup/originals.

### Phase 4: Cleanup

- Only after release manifests exist.
- Clean previews, old run reports, and old backups according to policy.

## Acceptance Criteria

The implementation is acceptable when:

- every important folder has a documented data class
- temporary folders are no longer treated as durable knowledge
- generated source pages provide direct Obsidian links to full source text
- cleanup policy is explicit but not destructive by default
- rollback is defined at release level
- the system can explain which data must be backed up and why
